# MeshLLM integration investigation

## Status

This document records the implementation boundary found in the PAIR source tree
and the evidence still required before MeshLLM can be added as an engine. It is
not an implementation plan approval and it does **not** claim that legacy NVIDIA
GPUs are inference-ready. In particular, hardware inventory, GPU telemetry, and
model routing do not select a CUDA, Vulkan, ROCm, or CPU runtime.

The intended topology is independent inference, not pooled memory: each model
instance belongs to one engine on one node and PAIR routes a request only to a
node that advertises that model. A GTX 980, GTX 1070, and RTX 2080 Ti can
therefore serve different requests and models, but PAIR must never present their
VRAM as a single device or split one inference across them.

## What PAIR does today

### GPU inventory and readiness data

`nvpair-node-info` discovers NVIDIA devices through `nvidia-smi` on Linux and
reports a name and total VRAM. The NVIDIA UUID is retained only as an internal
join key for dynamic statistics; it is deliberately not part of the HTTP
response. If `nvidia-smi` is unavailable, the Linux fallback reports adapter
names but neither VRAM nor a join key. This is telemetry and inventory, not a
capability probe and not an inference-device assignment.

The scanner enriches nodes with node-info telemetry and separately retrieves a
model inventory from engine-manager. The retrieved inventory has a flat model
union plus a per-engine mapping and a per-engine loaded set. This establishes
the important boundary: PAIR knows which engine advertises a model, but has no
wire field for the runtime or physical GPU that engine selected.

### Discovery, engines, and routing

PAIR currently defines two engine facades: Ollama and LM Studio. The engine
manager manifest launches those applications as their own local processes, and
the proxy applies a profile to each facade. The proxy only admits nodes whose
per-engine inventory advertises the requested model. It then applies manual
selection, scheduler priority, and deterministic ordering inside that owner
set. The scheduler ranks node pressure from compact GPU telemetry; it does not
model VRAM capacity, compute capability, or device affinity.

Consequently, no source path in this checkout rejects the GTX 980, GTX 1070, or
RTX 2080 Ti by architecture name or compute capability. PAIR's routing contract
is based on the engine's advertised model inventory; the model does not have to
be resident at the instant PAIR first observes the engine, but a request is only
eligible when the selected engine advertises that model. A failure to initialize
CUDA or Vulkan is owned by that engine or by a MeshLLM runtime, not by the PAIR
node scanner or scheduler.

### Network boundary

PAIR's cluster transport already treats reachability separately from discovery:
remote model inventory is fetched through pinned mutual TLS, while LAN discovery
uses mDNS. The local address-selection helper deliberately avoids publishing
virtual/VPN interfaces such as `tailscale` and `tun` as ordinary LAN candidates.
That is not a statement that Tailscale addresses can never be used: an explicit
manual-node or separately authenticated transport can still target a Tailscale
endpoint. The important boundary is that PAIR must not silently change its
cluster trust policy merely because an interface happens to be a tailnet
interface. A cross-network design must either use PAIR's explicit/manual-node
path or add a reviewed, authenticated transport/discovery design; it must not
make the desktop choose a Tailscale address or bypass PAIR's cluster trust.

## MeshLLM facts established from the integration fork

The current integration work is pinned to MeshLLM fork branch
`pair-mixed-gpu-integration`, head `5a6a170d663b5ded5822630999c4e41c25dac8e9`,
corresponding to MeshLLM PR #1. The source confirms that Tailscale discovery and
a Tailscale-only join-bootstrap path are being added, while the native runtime
loader remains process-global. The fork therefore treats mixed CUDA/Vulkan
execution as a separate-worker/process concern rather than claiming one process
can independently load both backends.

This document is an integration evidence record, not a claim that physical GTX
980/GTX 1070 inference has already passed. Before changing PAIR, keep collecting
all of the following against the pinned MeshLLM revision:

| Question | Evidence required | Why it changes the design |
| --- | --- | --- |
| Build selection | Build scripts, package manifests, and generated artifacts for CUDA, Vulkan, CPU, and ROCm. | Separate executables/libraries imply process-level selection; one fat binary may still impose a global runtime. |
| Runtime packaging | Resolver source, its compatibility inputs, downloaded artifact names/checksums, and environment variables. | Determines whether CUDA and Vulkan payloads can coexist on one host without library-path collisions. |
| Device discovery | Device enumeration source and the exact identifier passed between discovery and worker creation. | Shows whether MeshLLM can distinguish the GTX 1070 from the GTX 980 stably. |
| Worker boundary | Process tree, command arguments, inherited environment, dynamic-library loading, and whether a worker owns one device or all devices. | A process-global backend cannot safely implement CUDA for one GPU and Vulkan for another in the same worker. |
| Model assignment | Model-load API/schema and persistence format. | PAIR needs an advertised model-to-engine endpoint, not a guess based on total host VRAM. |
| Scheduler boundary | Queue/selection source and its public API. | Avoids duplicating MeshLLM's device scheduler inside PAIR or PAIR's node scheduler inside MeshLLM. |
| HTTP/API surface | OpenAI/Ollama compatibility, authentication, streaming semantics, health/model-list endpoints, and error shapes. | Decides whether MeshLLM can be a PAIR engine facade or needs a dedicated proxy adapter. |

The exact failure record is also required: OS and version, kernel, NVIDIA driver,
CUDA toolkit/runtime version, Vulkan loader/driver version, MeshLLM revision and
artifact, GPU UUIDs, backend-selection configuration, complete sanitized stderr,
and a minimal model-load command. The record must exclude prompts, model input,
credentials, pairing PINs, certificates, and key material.

## Mixed-GPU decision gate

The desired assignment, GTX 1070 to CUDA and GTX 980 to Vulkan on the same host,
is valid only if one of the following is demonstrated:

1. **One MeshLLM process supports per-worker backend selection.** Each worker
   receives both a stable device identifier and a backend/runtime choice, and
   its dependency loader is proven safe when CUDA and Vulkan are active.
2. **Separate MeshLLM processes support one backend each.** The CUDA process is
   constrained to the GTX 1070 and the Vulkan process to the GTX 980. Each
   exposes an independent model inventory and endpoint, so process-global
   runtime state is isolated.

Until source and a physical test prove either case, assume neither. In
particular, a resolver selecting one runtime artifact for a whole installation
does not prove per-GPU selection, and two detected GPUs do not prove that a
single runtime can execute on both.

## Integration options

### MeshLLM as a PAIR engine (preferred if it has a stable local server API)

Add MeshLLM as a third engine only when it has a documented, stable local
process lifecycle plus model-list and inference APIs. Engine-manager would own
the MeshLLM process(es), the proxy would add a MeshLLM facade/profile, and the
scanner would keep using the existing `modelsByEngine` contract. This retains
PAIR ownership of node discovery, trust, model-aware node selection, retries,
and cluster scheduling. MeshLLM owns device discovery, backend resolution,
per-device worker lifecycle, and model placement. A mixed-GPU host may need
multiple MeshLLM instances, but they must still report under one explicit
MeshLLM engine contract rather than pretending to be Ollama or LM Studio.

### MeshLLM behind an existing compatible facade

If MeshLLM provides a fully compatible and tested Ollama or OpenAI server, it
could initially be externally managed behind the corresponding existing PAIR
facade. This avoids a new PAIR protocol, but loses device/backend status and
cannot make MeshLLM first-class. It is acceptable only as a validation harness,
not as the integration target, because PAIR would be unable to distinguish a
MeshLLM failure from the emulated engine.

### Embedded MeshLLM

Do not embed MeshLLM into Electron, the broker, or a PAIR Go worker unless its
upstream architecture explicitly requires it and supports that embedding model.
Embedding would combine native-runtime loading, GPU fault isolation, and
MeshLLM's device scheduler with PAIR's control-plane process. It conflicts with
PAIR's existing rule that the broker supervises workers and engine-manager owns
engine lifecycle.

## Tailscale deployment comparison

Tailscale should provide private IP reachability; it should not become PAIR's
identity, scheduler, or discovery authority. PAIR cluster pairing and pinned
mutual TLS remain required even when the underlay is a tailnet.

| Deployment | Benefits for PAIR/MeshLLM | Costs and appropriate use |
| --- | --- | --- |
| Install Tailscale on every physical PAIR/MeshLLM host | Each node has an individual tailnet identity and direct encrypted reachability; simplest mapping from a PAIR node to a reachable host. | Requires installing and updating the client on every host. This is the default to validate first. |
| Dedicated subnet router/gateway | Reaches existing LAN-only machines without installing Tailscale on them. | The gateway is an extra failure domain and PAIR sees ordinary routed IPs, not per-node tailnet identities. Use for constrained hosts, not as a replacement for direct node identities by default. |
| Userspace networking | Can operate where a TUN device is unavailable. | It normally requires an application-level proxy/listener model, so it must be tested against PAIR's mTLS endpoints and MeshLLM streaming rather than assumed to be transparent. |
| Containerized Tailscale | Separates Tailscale lifecycle from the inference host process. | Requires deliberate network namespace, socket, capability, and route design. It does not remove the need for GPU-device access in the MeshLLM container/process. |
| Proxmox guest | Keeps the Proxmox host small while placing Tailscale and PAIR/MeshLLM in a supported guest OS. | GPU inference requires a VM with PCI passthrough or a deliberately configured LXC; validate NVIDIA driver, device nodes, cgroups, and kernel-module requirements. |

Subnet routing is useful when a node cannot run Tailscale. It is not a VRAM or
inference routing mechanism, and it is usually less direct than giving every
machine that runs PAIR or MeshLLM its own tailnet identity. MagicDNS can make
operator configuration easier, but PAIR should consume a resolved endpoint
through an explicit, trusted node configuration rather than alter its routing
policy based on a hostname suffix.

## Proxmox investigation gate

No reproducible Proxmox failure is recorded in this checkout. It is therefore
not possible to identify whether the failed component was Tailscale, MeshLLM,
an NVIDIA driver/CUDA package, or a container runtime. Do not label Proxmox VE 8
or Debian 12 unsupported without the failed command and output.

For a reproducible comparison, run the same pinned MeshLLM artifact and
configuration on: (1) the known-good Ubuntu 22.04 system; (2) an Ubuntu 22.04
VM on Proxmox with GPU passthrough; (3) an Ubuntu 24.04 VM with the same test;
and only then (4) a Debian 12 VM/LXC where the required GPU and container
prerequisites can be met. Record package repositories, package names and
versions, init-system assumptions, kernel and headers, NVIDIA driver state,
CUDA/Vulkan loader state, `/dev/nvidia*` and `/dev/dri` visibility, and whether
the installation expects Docker or systemd. This separates guest-OS support
from host hypervisor, passthrough, and unprivileged-container limitations.

## Required proof before changing the PR out of draft

1. Pin and inspect the MeshLLM source/revision and resolve the decision gate
   above. The current source evidence points to separate MeshLLM worker/process
   boundaries for mixed CUDA/Vulkan; that remains an implementation requirement,
   not a completed physical validation.
2. Prove one model load and inference on each physical lane: GTX 980 with the
   selected backend, GTX 1070 with the selected backend, and RTX 2080 Ti with
   its selected backend.
3. Prove the mixed GTX 1070/GTX 980 host runs the two assigned backends at the
   same time without device cross-selection, runtime-loader conflict, or VRAM
   pooling.
4. Prove the MeshLLM process advertises each loaded model through the selected
   PAIR engine integration.
5. Prove a paired remote node discovers that model, sends a request through the
   PAIR proxy, and receives a successful response. Test an unavailable model
   separately to verify that candidate selection does not broaden beyond model
   owners.
6. Keep physical GPU workflows manual and self-hosted. Hosted CI can validate
   contracts and fixtures, but cannot substitute for device/runtime inference.

## Current integration status

The MeshLLM Tailscale work is an implementation PR, not yet proof that PAIR can
route production inference to mixed CUDA/Vulkan workers. The current sequence is:

`Tailscale membership/trust → MeshLLM peer discovery → Tailscale-only join bootstrap
→ existing invite-token authentication → normal mesh membership`.

PAIR should integrate at the engine/process boundary only after the model-list,
health, streaming, failure, and worker-isolation contracts have been demonstrated.
The Tailscale path must remain an explicit opt-in trust mode and must not turn
arbitrary tailnet membership into MeshLLM worker authorization.

Physical GTX 980, GTX 1070, and RTX 2080 Ti inference remains a separate manual
self-hosted validation gate.

Do not mark the legacy-GPU pull request ready until all six proofs are attached
to the change review with sanitized logs and the exact runtime/build evidence.
